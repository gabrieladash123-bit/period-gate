# PeriodGate protocol

PeriodGate maintains a bounded candidate configuration of independent, fully preemptible sporadic tasks on one unit-speed processor. It is a reservation admission planner: it does not dispatch jobs, measure runtime, or verify actual execution. Each configuration must be applied from an empty backlog/quiescent boundary. Dynamic changes with carry-in jobs require a separate transient analysis.

The immutable constructor catalog fixes 2–6 task identifiers, commit-pinned specification URLs, raw SHA-256 hashes and reservation-owner wallets. Only the corresponding owner can activate or release a reservation. There is no administrator edit API, dependency graph, transferable certificate, credit queue or auction. State consists of the active set, a 60-point demand envelope, cached consensus interpretations and an append-only decision history. Each reservation has an independent budget of three activations, so one owner cannot consume another reservation's budget. A capacity-rejected task cannot retry until the configuration revision changes. Owner releases remain available after activation budget exhaustion. At most 18 activations and 18 releases can exist.

On first activation, GenLayer leader and validators independently fetch the complete specification and verify its raw hash. Each independently distinguishes a worst-case CPU execution bound from observations/averages, a relative completion deadline from a period, and a minimum inter-arrival time from a throughput target. The source must explicitly support independent, preemptible, non-suspending execution without blocking. Four material source quotations are checked against the full text. Exact agreement on normalized integer milliseconds and applicability is required; validators additionally audit the leader's quotations. Missing bounds or unsupported model assumptions yield UNRESOLVED and cannot reserve capacity. Complete numeric models outside the finite policy yield UNSUPPORTED.

For a supported task (C,D,T), 1 <= C <= D <= T and T must divide 60 ms. Each activation computes, for every integer t=1..60, the offered demand sum max(0, floor((t-D)/T)+1)*C over active reservations plus the candidate. If any demand exceeds t, the task stays WAITING and the earliest violating horizon and per-task demands are retained. Otherwise its reservation becomes ACTIVE and the whole demand envelope changes. Admission order is explicit first fit; the contract does not optimize which set to admit. An owner release subtracts the reservation. A waiting or released task can retry using its immutable cached interpretation. A caller-supplied expected revision prevents stale configuration changes. Revision increases only when the active set changes; unresolved and capacity-rejected decisions retain history but do not change the envelope.

The standard processor-demand criterion for constrained-deadline sporadic tasks under preemptive uniprocessor EDF is described in [Casini et al., Handling Transients of Dynamic Real-Time Workload Under EDF Scheduling](https://retis.santannapisa.it/~giorgio/paps/2019/TC19.pdf). The finite extension used here follows directly from the imposed period grid: for t>=0, dbf(t+60)=dbf(t)+U60, where U60=sum(C*60/T)=dbf(60). If every checked point satisfies dbf(t)<=t, then U60<=60. Writing any future horizon as 60n+r extends the bound by n*U60<=60n. All jumps occur at integer milliseconds, so checks at integer points also cover intermediate real horizons. This is exact for this restricted mathematical model, not a general EDF theorem implementation with arbitrary periods or hardware overhead.

The source publisher is responsible for the declared bounds and task independence; consensus verifies what the document supports, not the truth of a hardware WCET claim. Consumers must select trustworthy specifications and account externally for context-switch overhead, shared resources and actual application transitions. Synthetic fixtures demonstrate semantic extraction and capacity accounting only. A utilization below 100% is insufficient when short deadlines concentrate demand; the proofs include a 60%-utilized pair requiring 6 ms by a 4 ms deadline. A separate accepted configuration fills exactly 60/60 ms.

Generic MIT CLI transport and direct-VM helpers are reused from DeltaBisect. The fixed-grid demand-envelope ledger, capacity witnesses, owner releases, cached retries and exact specification interpretation are implemented for PeriodGate. EDF demand analysis is established scheduling mathematics; no claim of inventing it is made.
